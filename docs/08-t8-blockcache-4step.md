# 08 · T8 BlockCache 四步实测：43% 提速就在眼前，但有两个坑

> 2026-09-01 补做的研究。此前结论「T8 需等 ComfyUI ≥0.34」是**误判**——节点在 v0.33.1 上就能用，真正的问题出在别处。

## 先纠正上一版的两个误判

1. **「T8 依赖 v3 Layers API，当前版本不可用」——错**。实测 v0.33.1 的 `nodes.py` 完整支持 v3 节点协议（`comfy_entrypoint`），`comfy_api.latest.io` 符号齐全，T8 包四步加载（import → entrypoint → get_node_list → define_schema）全通，节点正常注册进 `/object_info`。
2. **但 v3 节点有一个真坑**：走 `/prompt` API 提交时**不应用服务端默认值**——`INPUT_TYPES` 里声明的全部参数（含 `advanced: True` 的）必须显式给全，缺一个就 400 `required_input_missing`。当年「节点静默不可用」的体感很可能来自这里。

## 实验设计

- 环境：2080Ti 22G / ComfyUI v0.33.1 / W4A8 mixed + fl2v Turbo 4step LoRA @1.0 / 640×352 · 124 帧 · `simple` 4 步 · `res_multistep`
- 同一工作流、同 seed 3013，唯一变量是 T8 节点及其参数
- 计时为热运行（模型已在显存中）wall clock

## 数据

| 配置 | 时长 | vs control | cache 命中 | 与 control 帧差 |
|---|---|---|---|---|
| control（无 T8） | **280s** | — | — | 基准 |
| T8 默认参数（threshold 0.12） | 290s | +3.6% | **0/4** | **零差异**（JPEG 级相同） |
| T8 中间档（threshold 0.45） | 220s | **-21%** | 1/4 | 未测（轨迹已分叉） |
| T8 激进（threshold 1.0, start 0, end 1.0, hits 10） | **160s** | **-43%** | 2/4 | 同质量的不同画面（见下） |

日志里的关键一行（激进档）：

```
MiniMax H3 Block Cache - cached 2/4 model forwards, cache 175.4 MiB on cpu
```

4 步里第 2、4 步的 block 计算被残差复用跳过，单步从 60-70s 掉到 ~1.2s——这就是 43% 的全部来源。

实测三档呈干净的单调曲线：**每次命中约省 60s（一次完整 forward）**，提速全部来自命中数——0/4 慢 3.6%（纯开销）、1/4 快 21%、2/4 快 43%。

## 阈值 × 场景运动强度矩阵（2026-09-02 补测，结论固化）

不同运动强度的镜头 × 不同阈值，命中率统计：

| 场景 | threshold 0.45 | threshold 1.0 | 备注 |
|---|---|---|---|
| 静态（晨雾湖面，几乎无运动） | **2/4** | 2/4 | 静态内容残差稳定，0.45 也能吃满 |
| 轻运动（雾中竹林走剑客） | 1/4 | 2/4 | |
| 中运动（集市行走+跟拍） | 1/4 | 2/4* | *1.0 档为两晚多次实测，全场景稳定 2/4 |

**结论**：命中率 = f(场景运动强度, 阈值)。**0.45 是"看镜头内容"的运气档**（静态吃满、一动就掉到 1/4）；**1.0 是无条件的稳定档**（任何场景 2/4）。产线选型不必看镜头下菜——**草稿档一律 1.0**，简单粗暴且上限一致。

方法学备注（复现者少踩坑）：
- verbose=False 时节点**不输出** "cached X/4" 汇总行——统计命中率必须 verbose=True
- 实测速度受环境影响极大（杀软实时防护未关时单镜可从 200s 漂到 500s+，且 ComfyUI HTTP 接口会迟滞超时）；本矩阵的**命中数不受环境影响**，速度以 09-01 干净环境数据为准

## 为什么默认参数一次都命中不了

T8 的命中条件是「音频/视频稳定性指标 < `residual_diff_threshold`（默认 0.12）」。日志显示本镜头 4 步的 diff 值在 0.39~1.00 区间——**4 步 Turbo 的步距（Δt）太大，每步之间残差变化剧烈，0.12 的阈值在数学上不可能满足**。这个默认值是为 8 步以上（官方加速 LoRA 场景）或 20-50 步标准路线设计的。

注意 diff 值有镜头内方差且前缀敏感：本 seed 下中间档（0.45）只吃到 1 次命中（那步 video_diff 0.608 越过了 0.45），全吃需要 threshold ≥ 1.01。**4 步路线想要稳定 2/4，直接用 1.0**；0.45 属于「看运气」档。

## 质量分析（重要）

激进档与 control 的帧差 PSNR 只有 14dB——这个数字**不能**读成「画质崩坏」。目检三帧（首/中/尾）：构图完整、无撕裂、无伪影、无色彩异常。真实原因是**采样轨迹分叉**：命中 cache 的步复用了上一步残差，数值路径从此不同，同 seed 也产出内容有偏移的不同视频——质量同级，内容不同。

音频同理会漂：激进档 mean −22.2dB / max −8.5dB（control 为 −14.0dB / −0.6dB），**无削波无爆音**，响度低约 8dB，后期统一响度即可。

## i2v（图生视频）路线同样有效（2026-09-02 补测）

同方法搬到 i2v（首帧锚定，锁脸镜头主力路线），同 seed 同默认首帧，热运行：

| 配置 | 时长 | 命中 |
|---|---|---|
| i2v control（无 T8） | **420s（7.0 min）** | — |
| i2v + T8 阈值 1.0 | **260s（4.3 min）** | 2/4 |

**-38%**。比例略低于 t2v 的 -43%，原因是首帧条件编码的固定开销（约 80s）不参与缓存；但**绝对节省 160s/镜比 t2v 的 120s 更多**——镜头越贵，T8 省得越多。草稿/成片双档用法与 t2v 完全相同。

## 两个必须知道的坑

1. **同 seed 不可复现**。命中 cache 后数值轨迹改变，同 seed 重跑 ≠ 同结果。产线依赖「失败镜头同 seed 重提」的断点续跑策略在 T8 档**失效**——重试会得到不同画面。
2. **同 seed 也不可与无 T8 版本对拍**。审片通过的 T8 版镜头，无法用无 T8 工作流复现出来。

## 实操建议（4 步 Turbo 路线）

- **草稿/预览/选镜头**：T8 激进档（threshold 1.0），**2.7 分钟/镜**，快 43%
- **成片镜头**：无 T8，保可复现性与审片一致性（5.7 分钟/镜）
- 默认参数（0.12）在 4 步路线上**没有任何意义**：0 命中 + 175MB 缓存管理开销，反而慢 3.6%
- 等 PDD LoRA（8 步）上线后重测：T8 + 官方加速 LoRA 是官方宣称的 +100% 组合，届时本文数据全部要重跑

## 复现

节点插入位置：Turbo LoRA 之后、Guider/Scheduler 之前（MODEL 链串联）。

```json
"200": {"class_type": "MiniMaxH3BlockCacheT8", "inputs": {
    "model": ["105:201", 0],
    "residual_diff_threshold": 0.45,
    "start_percent": 0.0, "end_percent": 1.0,
    "max_consecutive_hits": 10,
    "cache_device": "cpu", "metric_stride": 8, "verbose": true}}
```

（v3 API 节点：所有参数一个都不能省，包括 `advanced` 项。）
